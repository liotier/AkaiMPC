# MPC export: naming scheme, bulk export, published pack

Specification for implementation. Status: agreed, not yet implemented.

## 1. Provenance

A user of the MPC XL, posting as Elektrobolt on the MPC-Forums "Thoughts on the
MPC XL" thread, downloaded several hundred `.progression` files from this
generator, discovered that they navigate badly on the device, and relabelled
them by hand. He then described the labelling system he had arrived at.

His central observation, which this specification is built on:

> File names themselves don't seem to matter much to the MPC, but the name field
> inside each .progression JSON file definitely does - that's what the MPC parses
> during startup. The first dash appears to split the main menu category from the
> actual progression name, and everything after that is used for the progression
> submenu.

That observation comes from one user on one device. Section 4 lists what remains
unverified and how this design stays safe regardless of the answers.

## 2. The defect

`downloadSingleProgression()` (`app.js:1859`) and `exportProgressions()`
(`app.js:2402`) both set the JSON `name` field to the sanitised *file* name,
built by `getVariantFileName()` (`app.js:1852`), which converts the em dashes of
the roman numerals into hyphens. Under Elektrobolt's rule, every file this
generator has ever emitted produces a nonsensical menu heading:

| Emitted `name` | MPC heading | MPC submenu item |
|---|---|---|
| `A_i-♭VII-♭VI-V_Smooth-1` | `A_i` | `♭VII-♭VI-V_Smooth-1` |
| `C_I-vi-IV-V_Jazz-3` | `C_I` | `vi-IV-V_Jazz-3` |
| `C_Major_Scale-Exploration-1` | `C_Major_Scale` | `Exploration-1` |

This is not a matter of taste. The user's manual relabelling repairs our output.

## 3. Decisions

These are settled. Do not revisit them during implementation.

| # | Decision | Rationale |
|---|---|---|
| D1 | The JSON `name` field and the file name are **decoupled**. | They serve different consumers: `name` drives the MPC menu, the file name only has to be unique and filesystem-legal. Conflating them is the root cause of §2. |
| D2 | The `name` field always carries **canonical English**, whatever the interface language. | The MPC menu is a shared namespace. Localised exports would split one genre into two headings on a mixed collection, and community-shared archives would become a language salad. |
| D3 | **No key** in the `name` field; the key stays in the file name. | Pad Perform > Progressions transposes an imported `.progression` to the selected root note, preserving intervals and voicings. The key is therefore decorative in the menu and merely disambiguating on disk. |
| D4 | Roman numerals keep **♭ (U+266D)**. | The only empirical evidence we have says it renders on an MPC XL. `musicTheory.js:2489` keeps *chord names* ASCII; that policy is unchanged, and the `name` field is a different field. Reversible in one line if anyone reports mojibake. |
| D5 | Variants are numbered by **fixed style rank**, not by position. | See §5.2. |
| D6 | The published pack is **one zip**, built by CI, not per-genre. | Users prune. |
| D7 | The pack is **generated by CI at deploy time**, not committed. | Static files generated once, no binary churn in git. |
| D8 | The in-app bulk export buttons are **links to the CI-built static files**. They generate nothing. | One producer, so there is nothing to drift against. No client-side bulk generation, no progress UI, no JavaScript for this feature at all. |
| D9 | The `.progression` pack ships **the key of C only**; the MIDI pack ships **all twelve keys**. | The MPC transposes on import (D3), so a second key would be pure duplication. A DAW does not, so for MIDI the key is load-bearing. Measured: twelve keys of MIDI is 8280 files and 4.1 MB uncompressed - cheap enough that withholding eleven of them would be false economy. |

Note on D8: an earlier draft had the buttons generate the catalogue in the
browser, and justified extracting the generation core as the way to keep the two
producers in step. That was wrong - a button that points at the static file is
not a second producer. What genuinely must not drift is the *naming*, because the
app's single-progression and current-selection exports keep generating files
client-side, and those land in the same MPC folder as the pack. If they name
differently, one genre acquires two headings. `modules/mpcNaming.js` (§6.2) is
therefore the shared module that matters; the generation core is extracted for a
narrower reason, given in §6.1.

One consequence, raised and **accepted**: a link to a static file does not work
offline, so bulk export is unavailable to an installed PWA with no network.
Judged too niche to design around. The single-progression and current-selection
exports are unaffected, so the offline app still exports - just not in bulk.

## 4. Unverified assumptions

None of these block implementation. The design is safe under every answer, but
each is cheap for an MPC owner to settle and would let us relax a constraint.

| Assumption | Consequence if false | Test |
|---|---|---|
| The **first** hyphen splits heading from item, and later hyphens are preserved verbatim in the submenu label. | If the MPC splits on *every* hyphen, our one-hyphen invariant (§5.1) already protects us. If it splits on the *last*, likewise. The invariant is safe under all three readings. | Install one file named `Test-Doo-Wop 1 Smooth (I vi IV V)`. If the submenu shows `Doo-Wop 1 Smooth (I vi IV V)`, we may relax the sanitiser to the category only and restore hyphens in nicknames. |
| U+266D renders on MPC One / Live / X, not only on the XL. | Fall back to ASCII `b` in `MPC_NUMERAL_MAP` (§5.4), a one-line change. | Install one file with `♭` in the name on an older device. |
| The MPC does not truncate long menu labels. | Our longest generated label is 73 characters. If truncation bites, drop the parenthesised numerals from the label. | Install `Jazz/Functional-Secondary Dominant Chain 5 Experimental (V7/ii V7/V V7 I)` and look at it. |
| The MPC parses 690 files at startup without material delay or a hard limit. | Document a warning in the pack README and advise pruning. | Install the full pack and time the boot. |
| The MPC accepts arbitrary strings in the `scale` field (e.g. `Hirajoshi`, `Bhairav`, `Diminished (W-H)`). | Scale Mode exports (§5.5) may need `scale` pinned to a value the MPC knows. Progression Palette exports already emit `Major` and are unaffected. | Install one Scale Mode export of an exotic mode. |

## 5. Naming specification (normative)

### 5.1 The one-hyphen invariant

**A generated `name` value contains exactly one HYPHEN-MINUS (U+002D), and it is
the category separator.** Every other hyphen occurring anywhere in the source
strings is replaced by a single space.

This matters because the catalogue violates it in eighteen places if left alone:

- Four category keys carry a hyphen: `R&B/Neo-Soul`, `Hip-Hop/Trap`,
  `Folk/Singer-Songwriter`, `Italo-Disco/House`.
- Fourteen nicknames carry a hyphen: *50s Doo-Wop, 12-Bar Blues, 2-5-1,
  Tritone ii-V-I, Neo-Soul Standard, One-Chord Funk, Two-Chord Funk,
  Minor-Major Funk, Jazz-Funk Turnaround, Lofi Hip-Hop, Post-Rock Build,
  Full-On, Jump-Up, Two-Chord Reggae*.
- One progression `value` is not a roman-numeral sequence at all:
  `'12-bar-blues'`, which carries two hyphens.

Elektrobolt hit the first class and resolved it by amputation, cutting
`Italo-Disco/House` down to `Italo/House`. Substitution preserves the sense:
`Italo Disco/House`.

Solidus (`/`) is retained in the `name` field - it appears in category keys and
in secondary-dominant numerals such as `V7/ii`, and there is no evidence the MPC
treats it specially. It must still be removed from file names.

### 5.2 Style rank

```
Smooth = 1,  Classic = 2,  Jazz = 3,  Modal = 4,  Experimental = 5
```

Elektrobolt numbered his files positionally (`1 Smooth`, `2 Classic`, `3 Jazz`,
`4 Modal`). Positional numbering is unstable here, because
`deduplicateVariants()` (`app.js:1793`) drops variants whose chords collapse onto
an earlier variant's. Measured over the full catalogue in C: **865 variants
generated, 690 survive**, and the surviving set differs per progression:

| Surviving styles | Progressions |
|---|---|
| Smooth, Classic, Jazz, Modal, Experimental | 55 |
| Smooth, Classic, Jazz, Modal | 50 |
| Smooth, Classic, Jazz | 49 |
| Smooth, Classic, Jazz, Experimental | 13 |
| Smooth, Classic, Modal | 4 |
| Smooth, Jazz | 1 |
| Smooth, Classic | 1 |

Under positional numbering, Experimental is `4` in thirteen progressions and `5`
in fifty-five. Fixed rank makes the number stable across exports and forces the
app's intended ordering rather than the alphabetical one the MPC would otherwise
impose (Classic, Experimental, Jazz, Modal, Smooth).

Gaps in the numbering are acceptable and informative: `1 Smooth, 2 Classic,
3 Jazz, 5 Experimental` correctly signals that Modal collapsed onto another
variant.

### 5.3 Display name grammar (Progression Palette Mode)

```
name := mpcSafe(category) "-" mpcSafe(nickname) " " rank " " style " (" mpcSafe(value) ")"
```

- `category` - the key of the `progressions` object in `modules/musicTheory.js`,
  verbatim, **not** the translated `progressionCategories.*` string (D2).
- `nickname` - `progressions.<category>.<value>.nickname` from `locales/en.json`,
  **always the English file** (D2). All 173 progressions have one.
- `rank` - from §5.2.
- `style` - the variant name, unlocalised.
- `value` - the progression template string from `musicTheory.js`.

### 5.4 The two sanitisers

```js
const EM_DASH = '—';

// For the MPC `name` field. Hyphen is reserved as the category separator.
function mpcSafe(s) {
    return String(s)
        .split(EM_DASH).join(' ')
        .split('-').join(' ')
        .replace(/\s+/g, ' ')
        .trim();
}

// For file names. Hyphen is free; the filesystem's reserved set is not.
function fileSafe(s) {
    return String(s)
        .split(EM_DASH).join('-')
        .replace(/[\\/:*?"<>|\u0000-\u001F]/g, '_')
        .replace(/\s+/g, ' ')
        .trim();
}
```

`mpcSafe` applies to the numerals segment as well as to the category and
nickname. This is what handles `'12-bar-blues'` correctly - it is a template
`value`, not a numeral sequence, and without the substitution it would smuggle
two extra hyphens into the label.

### 5.5 Scale Mode

Scale Mode has no genre. Use the mode's category from the `modes` object in
`musicTheory.js` as the heading, which mirrors the genre grouping:

```
name := mpcSafe(modeCategory) "-" mpcSafe(mode) " Scale"
```

giving `Common Western Tonal-Dorian Scale`, `Exotic-Hirajoshi Scale`,
`Symmetrical/Jazz-Diminished (W H) Scale`. Note that `mpcSafe` is doing real work
in the last of those: the mode names `Diminished (W-H)` and `Diminished (H-W)`
carry hyphens.

Scale Mode produces one variant, so there is no rank and no style segment.

### 5.6 File name grammar

```
file := fileSafe(key "_" category "_" nickname "_" rank style "_" value) ".progression"
```

The numerals are included because they are the only thing distinguishing the two
Jazz/Functional progressions that share the nickname **Extended Turnaround**
(`V7/ii—ii—V7—I` and `I—V7/vi—vi—V7/V—V7—I`). Omit them and those six files
collide.

The key is retained here, unlike in the display name, so that a user who exports
the same progression in several keys can keep them side by side on disk.

MIDI files follow the same grammar with a `.mid` extension, under a folder
named for the key (D9). The key stays in the file name too, so a file remains
identifiable once dragged out of its folder and into a DAW.

Truncate to 120 characters as `sanitizeFileName()` (`app.js:123`) already does,
but truncate **before** appending the extension, not after. The longest name the
catalogue currently produces is 84 characters.

### 5.7 Worked examples

```
Jungle/Drum'n'Bass-Liquid DnB 1 Smooth (i ♭VII ♭VI V)
Italo Disco/House-Classic Italo 2 Classic (I vi IV V)
Blues/Soul-12 Bar Blues 3 Jazz (12 bar blues)
Jazz/Functional-Extended Turnaround 1 Smooth (V7/ii ii V7 I)
Folk/Singer Songwriter-Post Rock Build 5 Experimental (I V vi IV)
Common Western Tonal-Dorian Scale
```

with file names such as

```
C_Blues_Soul_12-Bar Blues_3Jazz_12-bar-blues.progression
C_Jazz_Functional_Extended Turnaround_1Smooth_V7-ii-ii-V7-I.progression
```

### 5.8 Verified properties

Generated over the whole catalogue in C (690 files), by running the real
generation functions rather than by inspection:

- 0 duplicate display names
- 0 duplicate file names
- 0 display names containing other than exactly one hyphen
- longest display name 73 characters, median 51
- longest file name 84 characters

These four counts are the acceptance test in §9.

## 6. Code changes

### 6.1 Extract the generation core into a module (prerequisite)

`tools/build-pack.mjs` has to call the generator from Node, and it cannot import
`app.js`: line 2504 registers a `DOMContentLoaded` listener at module top level,
which throws the moment Node evaluates the module. The generation core therefore
has to leave `app.js`.

That is the whole justification. It is *not* a parity requirement - under D8
there is only one producer of the pack.

This is cheap, because the generation core is already free of the DOM. Verified:
the following ten functions in `app.js` contain no reference to `document` or
`window`, and depend on nothing outside `musicTheory.js` besides three pieces of
module state.

```
generateVariant              generateScaleExploration
selectDynamicRow4Chords      analyzeExistingChords
determineChordFunction       generateRow4Candidates
scoreCandidate               matchesChordRequirement
getChordProgressionSignature deduplicateVariants
```

Move them to `modules/generation.js`. Replace the reads of the module globals
`selectedKey`, `selectedMode`, `selectedProgression` and `chordRequirements` with
an explicit options object; `app.js` passes its globals in. `NOTE_PITCH_CLASSES`
(`app.js:557`) moves with them.

Proposed surface:

```js
export function generateVariants({ key, mode, progression, generationMode, chordRequirements = [] })
```

returning the deduplicated variant array, so callers stop repeating the
`['Smooth', 'Classic', 'Jazz', 'Modal', 'Experimental']` list.

Measured cost of the full catalogue through this path under Node: **278 ms for
690 variants**, and 9 ms for all 34 scale explorations. Building all twelve keys
of MIDI is therefore a few seconds of CI time.

One measurement worth carrying into §8: the surviving variant count is **not**
constant across keys - 690 in C, 700 in G, 728 in B, 690 in A♭. Identical
harmony, different enharmonic spelling, and `getChordProgressionSignature()`
keys on the chord name, so dedup outcomes diverge by key.

### 6.2 New module: `modules/mpcNaming.js`

Exports `mpcSafe`, `fileSafe`, `STYLE_RANK`, and

```js
export function buildMpcDisplayName({ generationMode, category, nickname, value, style, modeCategory, mode })
export function buildExportFileName({ key, category, nickname, value, style, modeCategory, mode, extension })
```

This module is the single authority on §5. Nothing else may assemble a name.

It needs a category lookup - given a progression `value`, find its category. The
existing code already does this inline in `generateVariant`; extract it as
`findProgressionCategory(value)` in `musicTheory.js` and use it in both places.

It also needs the English nicknames independently of the active locale. Import
`locales/en.json` directly rather than going through `i18n.t()`, which returns
the active language.

### 6.3 Collapse the duplicated payload builder

`downloadSingleProgression()` (`app.js:1859`) and `exportProgressions()`
(`app.js:2402`) construct the same JSON object twenty lines apart. Extract:

```js
function buildProgressionPayload(variant, { key, scale, name })
```

Both callers use it, and so does the CI build script. Without this the naming
rule will diverge between the single-file and the bulk paths within a month.

While in there: `fileName.replaceAll('.progression', '')` (`app.js:1865`,
`app.js:2416`) is a global replace standing in for an extension strip. Once the
name and the file name are decoupled it disappears entirely.

### 6.4 In-app bulk export links

Placement: at the **bottom of the page, immediately before `<footer>`** in
`index.html:176`, after `#progressionsContainer`. These are not the happy path -
they are an affordance for users who want to manage several hundred files by
hand - and the layout should say so. Style them as secondary, not `primary`.

They are anchors, not buttons in the behavioural sense:

```html
<a class="secondary" href="pack/AkaiMPC-Chord-Progressions.zip" download>...</a>
<a class="secondary" href="pack/AkaiMPC-Chord-MIDI.zip" download>...</a>
```

Show the one matching the active context tab (`index.html:153-157`): the
`.progression` pack under `data-context="mpc"`, the MIDI pack under
`data-context="midi"`, neither under Keyboard, Guitar or Staff. That visibility
toggle is the only JavaScript this feature needs.

Both labels must state what the link actually delivers, because neither honours
the key selector: the `.progression` pack is in C and the device transposes
(D3), the MIDI pack contains all twelve keys in folders (D9). A user who has
selected F♯ and gets a zip must not have to guess.

The existing `#downloadAllBtn` (`index.html:171`) is untouched. It exports the
currently generated variants in the selected key, client-side, and it must use
`modules/mpcNaming.js` so its output is indistinguishable from the pack's.

### 6.5 CI-built pack

New `tools/build-pack.mjs`, importing `modules/generation.js`,
`modules/mpcNaming.js`, `modules/musicTheory.js` and `modules/midiExport.js`.
It writes:

```
pack/AkaiMPC-Chord-Progressions.zip   690 .progression files, key of C, flat
pack/AkaiMPC-Chord-MIDI.zip           8280 .mid files, twelve folders, one per key
pack/README.txt                       install instructions, provenance, credit
```

Measured: 690 `.progression` files are 2.5 MB uncompressed, 328 KB zipped; the
twelve-key MIDI set is 8280 files and 4.1 MB uncompressed.

The `.progression` zip is flat because the MPC reads a flat `Progressions`
folder. The MIDI zip is foldered by key because a filesystem is not a menu and
8280 files in one directory helps nobody.

Wire it into `.github/workflows/deploy-main-production.yml` as a step before the
`peaceiris/actions-gh-pages` action, which publishes `.` with `keep_files: true`.
The zips are therefore served from GitHub Pages and never committed - satisfying
D7.

Use a fixed timestamp for every zip entry so successive builds of unchanged
content are byte-identical.

`README.txt` must credit Elektrobolt for the naming scheme and carry the startup
warning from §4.

### 6.6 i18n

New UI strings need entries in **all six** locale files (`en`, `fr`, `de`, `es`,
`it`, `pt`). `tools/check-translations.mjs` compares key sets across locales and
fails CI on any gap - see `.github/workflows/check-translations.yml`. Adding
English only will break the build.

Minimum new keys: the two button labels, a busy-state label, and a completion
notification. Consider also a one-line note explaining that exported names are
in English regardless of interface language (D2), which will otherwise look like
a bug to a French or German user.

## 7. Bug to fix in the same change

### 7.1 Smooth voicings drop a chord tone

`buildVoicingFromBass()` (`modules/musicTheory.js:2041`) places pitch classes
above the bass by iterating `uniquePCs` **from index 1**, regardless of where the
bass's own pitch class sits in that array. When the chosen bass is not the
chord's lowest pitch class, its pitch class is never placed and another is
doubled instead.

Concretely, `I—V—vi—IV` in C, Smooth variant, as currently shipped:

```
pad 1  C     60,64,67    C E G     correct
pad 2  G     59,67,71    B G B     no D
pad 3  Am    57,69,72    A A C     no E
pad 4  F     57,69,72    A A C     no F - and identical to pad 3
```

An F major chord containing no F, and two adjacent pads that sound the same.

The guard `if (voicing.length === uniquePCs.length)` in `generateSmoothVoicings`
(`musicTheory.js:2074`) counts notes rather than distinct pitch classes, so it
passes.

Scope: **1059 pads in the key of C alone**, confined entirely to the Smooth
variant. `optimizeVoiceLeading` and the Jazz, Modal and Experimental paths are
unaffected. Smooth is the first variant shown for every progression in the
catalogue.

Fix, verified over 137 264 pads across all twelve keys (0 remaining):

```js
function buildVoicingFromBass(bassNote, uniquePCs) {
    const bassPC = ((bassNote % 12) + 12) % 12;
    const bassIndex = uniquePCs.indexOf(bassPC);
    if (bassIndex === -1) return [];

    // Place the remaining pitch classes above the bass in chord order. Indexing
    // from 1 regardless of where the bass sits dropped the bass's own pitch
    // class and doubled another one instead.
    const remaining = [...uniquePCs.slice(bassIndex + 1), ...uniquePCs.slice(0, bassIndex)];

    const voicing = [bassNote];
    let currentNote = bassNote;

    for (const targetPC of remaining) {
        let nextNote = currentNote + 1;
        while ((nextNote % 12) !== targetPC && nextNote < bassNote + 24) {
            nextNote++;
        }
        if (nextNote < bassNote + 24) {
            voicing.push(nextNote);
            currentNote = nextNote;
        }
    }

    return voicing;
}
```

and in `generateSmoothVoicings`, replace the length check with

```js
// Count distinct pitch classes, not notes: a voicing that doubled one pitch
// class and dropped another used to pass this check.
if (new Set(voicing.map(n => ((n % 12) + 12) % 12)).size === uniquePCs.length) {
```

Rejecting more candidates is safe: `findBestSmoothVoicing()`
(`musicTheory.js:2179`) falls back to the unvoiced chord, which is musically
correct if less smooth.

Same progression after the fix - genuine voice leading, C held as a common tone:

```
pad 1  C     60,64,67    C E G
pad 2  G     59,62,67    B D G
pad 3  Am    60,64,69    C E A
pad 4  F     60,65,69    C F A
```

This belongs in this change rather than a later one because it corrupts the
files we are about to publish several hundred of.

## 8. Bugs found and deliberately deferred

A partial audit turned up a family of roman-numeral labelling errors. They are
**out of scope** here: they touch the UI, the tooltips and the palette-building
logic, and folding them into an export change would make review impossible. None
of them reaches the exported files - a `.progression` carries only `chordName`,
`role` and `notes`, and the numerals in the display name come from the authored
template string, which is correct.

They should get their own pass, and one of them should probably get it before the
pack is published, since a published pack is harder to correct than a web app.

1. **Chromatic degrees mislabelled.** `getRomanNumeralForChord()`
   (`musicTheory.js:2680`) maps a scale-step index onto `['I','II','III','IV',
   'V','VI','VII']` with no notion of chromatic alteration. In C major this
   yields `VI → Bb` (312 occurrences), and secondary dominants come out as
   `♭VII7 → B7` (205), `♭VI7 → A7` (149), `♭III7 → E7` (81), `♭II7 → D7` (43) -
   B7 is `V7/iii`, A7 is `V7/ii`, E7 is `V7/vi`, D7 is `V7/V`. Total 1127
   root-mismatched labels out of 10 637 pads checked in C.

2. **Duplicate harmony under different numerals.** The palette's uniqueness check
   is on the roman numeral, so `Bb` can appear as both `♭VII` (row 3) and `VI`
   (row 4) in the same card. Two of sixteen pads then sound identical, which
   defeats the stated purpose of the palette. This one also perturbs
   `getChordProgressionSignature()`, which keys on the chord name, and so lets
   near-duplicate variants survive `deduplicateVariants()`. The effect is
   measurable: the same catalogue yields 690 surviving variants in C, 700 in G
   and 728 in B. The harmony is identical in all three; only the spelling
   differs. A correct implementation would produce the same count in every key.

3. **Non-diatonic sevenths on the dominant.** Row 2 appends `M7` uniformly, so
   `V` becomes `VM7 → Gmaj7` in C major, introducing an F♯ into a row of
   otherwise diatonic seventh chords. The diatonic seventh on V is `V7 → G7`,
   which the same card also contains, at pad 13.

4. **Numeral not updated after a chord is upgraded.** In the Jazz variant, pad 10
   is labelled `ii` while carrying `Dm7`.

The audit was not exhaustive. It checked pad count, MIDI range, empty note
arrays, non-ASCII chord names and pitch-class completeness across all twelve keys
(8319 variants, 137 264 pads) - all clean apart from §7.1 - and roman-numeral
root consistency in C only.

## 9. Acceptance criteria

1. `node tools/build-pack.mjs` emits 690 `.progression` files in C and 8280
   `.mid` files across twelve keys, with **zero** duplicate display names,
   **zero** duplicate file names within any one key, and **zero** display names
   containing other than exactly one hyphen.
2. No pad in any variant, in any of the twelve keys, has fewer distinct pitch
   classes than its chord type requires. (Currently 1059 failures in C.)
3. `node tools/check-translations.mjs` passes.
4. A single-progression export taken from the running app carries a `name`
   field identical to the corresponding file in the pack. Assert it in a test
   that drives `modules/mpcNaming.js` from both call sites - this is the
   drift that actually matters (§3, note on D8).
5. A generated file loads in MPC Pad Perform and appears under the expected
   heading. Only an MPC owner can confirm this; it gates the release, not the
   merge.

## 10. Non-goals

- Per-genre pack splitting (D6).
- Localised export names (D2).
- Publishing the `.progression` pack in more than one key - the device
  transposes (D3). The MIDI pack is the exception, and D9 says why.
- Client-side bulk generation (D8), and with it any progress bar, worker or
  chunking scheme.
- Offline bulk export: the links point at static files (D8).
- Fixing the roman-numeral family (§8).
- Printable chord charts in the pack: `modules/rendering.js` builds SVG through
  the DOM and would need a headless browser, which the rest of this design
  avoids.

## 11. Credit

The naming scheme is Elektrobolt's, arrived at empirically by relabelling more
than three hundred files by hand. This specification changes three things about
it: hyphen substitution instead of amputation (§5.1), fixed style ranks instead
of positional numbering (§5.2), and the removal of the key from the label now
that transposition on the device is confirmed (D3).
